# Deep Research Agent 开工设计文档

> 定位：面试主攻项目。一个「给定问题 → 自主调研 → 产出带引用可验证报告」的通用研究型 Agent。  
> 版本：v0.1 草案 | 日期：2026-10-02 | 作者环境：Windows + Python 3.13 + ModelScope (openai_compatible)

---

## 1. 一句话面试叙事

「我做了一个端到端的研究型 Agent：LangGraph 状态机编排、MCP 协议工具层、混合检索 RAG、SSE 流式输出、token 预算熔断，并且有一套**引用可验证率**评估体系——这套评估方法论我在 TradingAgents-Astock 的数值溯源工作中已经验证过，这个项目是它的泛化。」

差异化点：**别人交 demo，你交 demo + 评估报告**。每个模块都留量化数据。

## 3. 系统架构

```
用户问题
   │
   ▼
┌─────────────────────────────────────────────┐
│  LangGraph 状态机                             │
│  planner → researcher(循环) → synthesizer    │
│              │            → verifier         │
│              ▼                                │
│  interrupt() 断点：高风险动作 human-in-loop   │
└──────────┬──────────────┬───────────────┬───┘
           ▼              ▼               ▼
      MCP 工具层      RAG 知识库       预算/守卫层
   search/browser/   BM25+向量+RRF    token 计量
   code-sandbox      + rerank         429熔断/预算熔断
           │              │               │
           ▼              ▼               ▼
        事实库(SQLite + 向量库)      trace(JSONL)
```

核心循环：planner 拆解子问题 → researcher 逐个调研（search → read → 摘要 → 引用入库）→ synthesizer 汇总成稿 → verifier 校验每个结论的引用真实性 → 不通过的结论打回重查（最多 N 轮）。

**关键设计决策（面试必讲）：**

1. **verifier 是独立节点而非 prompt 里一句"请核实"**——评估与生成分离，可独立测试
2. **引用格式强制结构化**：每个结论必须挂 `[cite:id]`，id 对应 SQLite 里的原文快照，机器可查
3. **预算熔断前置**：不是事后统计，而是每次 LLM 调用前检查预算余量，不足直接降级/终止（复用 429 停手纪律的工程化）

## 5. 核心模块要点

### 5.1 编排（graph/）

- 状态：`{question, subquestions[], findings[], citations{}, draft, verify_report, budget_used, ...}`
- researcher 内部 tool-calling 循环上限 8 步；同一子问题最多重查 2 次
- `interrupt()` 用在：单次运行 token 超阈值、需要访问付费数据源、verifier 连续失败

### 5.2 MCP 工具层（tools/）

- 所有工具实现统一接口：`async def run(params) -> ToolResult`
- ToolResult 强制带 `ok / error_type / latency / raw_len`——错误归一化才能讲"工具层可靠性设计"
- 超时 30s，重试仅限幂等操作（search 重试、browser 不重试）

### 5.3 RAG（rag/）

- 切分：500 token / 50 overlap，保留 URL + 原文哈希（溯源用）
- 检索：BM25 + bge 向量各取 top10 → RRF 融合 top20 → reranker 取 top5
- **面试问答准备**：「纯向量在专有名词/编号上召回差，BM25 补精确匹配；RRF 免调权」

### 5.4 引用与验证（verifier）

- 生成侧：prompt 强制 `[cite:N]` 格式，无引用的结论标 `unverified`
- 验证侧：独立 LLM 调用（或规则）核对「结论是否被该 citation 原文支持」，输出三分类：supported / partial / unsupported
- 报告尾注自动生成引用清单，每条带原文快照链接

### 5.5 守卫层（guard/）

- 预算：配置 `max_tokens_per_run`，provider 层每次调用前检查，超限抛 `BudgetExceeded` → graph 捕获后降级（停止调研、直接用已有材料成稿并标注"预算截断"）
- 注入防护：工具返回的网页文本进 context 前加隔离标记 + 输出侧过滤"忽略之前指令"类模式（做成可测试的规则函数，不吹成"绝对防御"）

### 5.6 工程化（server/ + trace/）

- SSE 事件类型：`plan / tool_call / tool_result / token / verify / done / error`
- 每次运行落一条 JSONL：问题、子问题数、工具调用次数、token 用量、耗时、验证通过率
- 这些 trace 数据直接喂给 evals——观测和评估共用一套底座

## 6. 评估体系（项目的灵魂）

指标定义（写进 README 的指标表）：

| 指标     | 定义                     | 目标           |
| ------ | ---------------------- | ------------ |
| 任务成功率  | 人工判定报告回答了问题            | ≥ 80%（30 题）  |
| 引用可验证率 | supported 引用数 / 总引用数   | ≥ 85%        |
| 幻觉结论率  | unsupported 结论数 / 总结论数 | ≤ 10%        |
| 检索命中率  | 金标准来源出现在引用中的比例         | ≥ 70%        |
| 单题成本   | token 消耗 / 题           | 报告均值即可，讲成本意识 |

数据集：30 个有客观答案的问题（技术/产品对比/时效性问题各 10），人工标注金标准来源。

**与 TradingAgents 的串联话术**：TradingAgents 里我做的是金融数值的溯源（每个数字指回数据源），这里是结论级引用验证——同一套"生成必须可追溯"方法论在不同粒度的落地。

## 7. 里程碑（4 周）

| 周  | 交付                                                     | 验收标准                     |
| -- | ------------------------------------------------------ | ------------------------ |
| W1 | 骨架：graph 跑通 planner→researcher→synthesizer，接 search 工具 | 单问题端到端出报告（无验证），trace 落盘  |

| W4 | evals 完整跑 + README（架构图/指标/demo GIF）+ 注入测试用例            | 指标达 §6 目标；README 可直接给面试官 |

每日纪律（沿用你的铁律）：429/余额不足立即停手，当日改做零消耗工作（写测试、整理文档、标注数据集）。

## 8. 风险清单

- ModelScope 限流 → 数据集批量跑放夜间 + 断点续跑（eval harness 支持从 JSONL 断点恢复）
- 网页读取失败率高 → 工具层已有错误归一化，eval 里单独统计工具成功率
- 范围膨胀 → sandbox 代码执行标记为可选，W4 有富余才做

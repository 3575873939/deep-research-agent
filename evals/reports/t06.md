# Cross-Encoder Reranker 与 Bi-Encoder 向量检索的成本-精度权衡报告

## 核心结论

1. **架构差异决定成本量级**：Bi-encoder 将查询与文档独立编码，文档向量可离线预计算，检索仅需向量相似度扫描，可扩展到数十亿文档、延迟为单数字毫秒级 [cite:722][cite:725]；Cross-encoder 将查询与文档拼接为单一序列共同过 transformer，每对 (query, document) 都需一次前向传播，无法预计算 [cite:722]。这是两者成本差异的根本原因。

2. **精度提升通常为个位数到约 20% 的相对提升**：在 ZeroEntropy 评测中，加入 reranker 使 NDCG@10 提升 5–20%，在法律、医疗、金融等语义更微妙的领域提升最大 [cite:712]；在 BEIR SciFact 基准上 recall@10 从 0.783 提升到 0.822（约 5%），代价是约 55 倍延迟（9.5 ms → 519 ms）[cite:713][cite:724]。

3. **成本随候选集规模线性增长**：Cross-encoder 对每个候选都要跑一次 Transformer 前向推理，候选 K=200 就要做 200 次前向推理 [cite:728]；成本方面，重排 top-100 文档约 0.001 美元，比单独向量搜索（约 0.0000002 美元/次）高出约 5000 倍 [cite:729]。

4. **rerank 只放最后一级的原因**：Cross-encoder 无法对百万级候选逐一打分（太慢），只能用于粗筛之后的少量候选精排 [cite:728]；Bi-encoder 则能支撑百万级候选集的快速召回 [cite:727][cite:730]。因此典型架构为「先粗筛、后精排」的两阶段 Retrieve & Re-Rank [cite:732][cite:734]。

5. **两阶段架构可有效平衡延迟与精度**：第二阶段通常仅增加 100–200 ms 延迟，在 LLM 生成已需 1–3 秒的场景中用户往往感知不到；若延迟预算极紧，可缩小候选集（如重排 20 个而非 50 个），通常能以一半延迟成本保留约 80% 的精度收益 [cite:735]。

## 分述

### 一、计算复杂度差异

Bi-encoder 与 cross-encoder 在计算复杂度上存在本质差异：

- **Bi-encoder**：查询和文档独立编码为向量，文档向量可预先计算，对海量文档的检索只需毫秒级时间（单数字毫秒），可扩展到数十亿文档 [cite:722][cite:725]。
- **Cross-encoder**：查询与文档拼接为单一序列共同通过 transformer，每个查询 token 都要关注每个文档 token，每对 (query, document) 都需一次前向传播，只能一次打分一对，无法预计算 [cite:722]。BGE 文档指出 cross-encoder 在数据量很大时极其耗时，因此通常先用 bi-encoder 初检（如从 10 万句中选 top 100），再用 cross-encoder 精排 [cite:723]。Weaviate 也指出 cross-encoder 需要对每个数据项与查询组合逐一计算，对成千上万或数百万对象而言不切实际 [cite:726]。

**具体延迟数据**：
- BEIR SciFact 数据集（5,183 文档、300 查询）基准测试：cross-encoder 相比 bi-encoder 延迟约高 55 倍（9.5 ms → 519 ms）[cite:724]。
- ZeroEntropy 生产模式数据：bi-encoder 约 5 ms 检索 top 100 候选，cross-encoder 约 50 ms 重排这 100 个候选 [cite:722]。
- Cross-encoder 不持久化任何向量，重排完全在运行时进行 [cite:724]。

### 二、检索精度提升幅度

Cross-encoder reranker 相比 bi-encoder 在检索精度指标上的提升幅度因数据集和指标而异，通常为个位数到约 20% 的相对提升：

- ZeroEntropy 评测：在 zembed-1 检索之上加入 zerank-2 使 NDCG@10 提升 5–20%（跨不同垂直领域），在法律、医疗、金融等查询更微妙的领域提升最大 [cite:712]。
- BEIR SciFact 数据集：recall@10 从 0.783 提升到 0.822（约 5%），precision 从 0.088 提升到 0.092，代价是约 55 倍延迟（9.5 ms → 519 ms）[cite:713]。
- 其他来源主要从架构原理上解释 cross-encoder 通过联合编码 query 和 document 实现更精确的相关性打分，但未给出具体量化提升幅度 [cite:714][cite:715][cite:716]。
- 另有基准测试显示，与仅用嵌入的方法相比，重排序可将检索精度提高 15–48%，NDCG@10 持续增长，并在不改变 LLM、提示词或分块策略的情况下将幻觉率降低 28–40% [cite:735]。

### 三、为什么 rerank 只放最后一级

Cross-encoder reranker 通常只作为最后一级重排，核心原因在于其架构决定了计算成本随候选集规模线性增长，无法支撑百万级候选的逐一打分：

- Cross-encoder 将 query 与文档拼接后输入同一个 Transformer，通过 token 级自注意力交互输出相关性分数，精度高于 Bi-encoder，但无法预计算，每个候选文档都必须与 query 现场拼接做一次前向推理 [cite:727][cite:728]。
- Bi-encoder 将 query 和文档独立编码成向量，文档向量可离线预计算，检索时只需编码 query 并做向量相似度扫描，速度极快，能支撑百万级候选集的检索 [cite:727][cite:730]。
- 因此 Cross-encoder 无法对百万级候选逐一打分（太慢），只能用于粗筛之后的少量候选精排 [cite:728]。

**计算成本与候选集规模的关系**：
- Cross-encoder 对每个候选都要跑一次 Transformer 前向推理，若候选 K=200，就要做 200 次前向推理，即使小 reranker 也很贵 [cite:728]。K 越大越准，但越慢 [cite:728]。
- 延迟方面：向量检索为毫秒级，加入 Cross-encoder Reranker 后延迟可能提高到几百毫秒甚至几秒，取决于模型大小和硬件性能 [cite:729]。
- 成本方面：向量检索每次查询成本极低（约 0.0000002 美元），而重排 top-100 个文档的成本高达 0.001 美元，比单独向量搜索高出约 5000 倍；即使只重排 10 到 20 个结果，费用仍远高于单纯向量搜索 [cite:729]。
- Reranker 的推理成本无法像 Embedding 那样复用离线索引结果，每次在线查询都要重新推理，带来重复开销，对高流量检索系统不适用 [cite:729]。

**工程折中**：用小模型（reranker-base）跑 50~200 个候选，或用更强 reranker 跑更小 K [cite:728]；典型两阶段方案为 BM25/向量召回 Top-K（如 200），合并去重后 Cross-Encoder rerank 到 Top-N（如 10）[cite:728]。评测显示第一阶段 top-k 值越大最终结果越好，但受限于 Reranker 的 latency 和 API 成本，top-k 10 太小，chunk 为 500 tokens 时可用 top-k 100，chunk 为 1000 tokens 时可用 top-k 50 [cite:731]。

### 四、两阶段架构如何平衡延迟与精度

在典型检索系统（如 RAG 或搜索引擎）中，两阶段架构通过「先粗筛、后精排」平衡延迟与精度：

**第一阶段（Bi-Encoder 快速检索）**：文档向量可预先编码并存储，查询时仅需编码查询文本并进行向量比较，成本近似 O(1)，可在 100 ms 内扫描数百万文档，适合从大规模候选集中召回 Top-K（如 Top-50～100）候选结果 [cite:732][cite:734][cite:735]。但 Bi-Encoder 独立编码查询与文档，二者在编码过程中从未交互，需在不知查询的情况下将文档压缩为固定向量，导致否定词、量词、领域术语等细微语义差异被模糊或丢失，精度相对有限 [cite:732][cite:735]。

**第二阶段（Cross-Encoder 精确重排序）**：将查询与文档拼接后联合输入 Transformer，通过自注意力机制建模跨文本交互，直接输出相关性分数，精度极高，能捕捉 Bi-Encoder 在向量近似检索中丢失的细微关系 [cite:732][cite:734][cite:735]。代价是计算开销大：每个查询-文档对都需独立前向传播，若重排 50 个候选文档就需 50 次顺序推理，CPU 上重排 30 个候选约需 100–150 ms，GPU 上约 30–50 ms，超过 100 个候选则仅重排步骤就超过 300 ms [cite:733][cite:735]。因此 Cross-Encoder 只用于对少量初筛候选进行二次评估，而非全库处理 [cite:734][cite:735]。

这种「Retrieve & Re-Rank」组合在 Google、Bing 等主流搜索引擎及各类 RAG 系统中广泛应用，有效实现速度与精度的最优平衡 [cite:732][cite:734]。

**关键权衡**：只需对一小部分候选集重排，第二阶段通常仅增加 100–200 ms 延迟，在 LLM 生成已需 1–3 秒的对话或搜索界面中用户往往感知不到；若延迟预算极紧，可缩小候选集（如重排 20 个而非 50 个），通常能以一半延迟成本保留约 80% 的精度收益 [cite:735]。此外，还可采用批次重排、结果缓存、分层服务（VIP 用户精排、一般用户快速检索）等成本控制策略 [cite:736]。

### 五、输入长度与批量大小的计算成本限制

Cross-encoder 类重排模型（如 bge-reranker）在推理时存在输入长度和批量处理方面的计算成本限制：

- **输入长度限制**：不同 Reranker 模型有各自的输入长度限制（查询与文档 chunk 的 token 总数），bge-reranker-base/large 仅支持 512 tokens，Jina 支持 1024 tokens，Cohere 支持 4096 tokens，Voyage 支持 8000 tokens [cite:720]。BGE 官方文档指出 bge-reranker-base（278M 参数）和 bge-reranker-large（560M 参数）是 cross-encoder 模型，"更准确但效率更低" [cite:721]。
- **计算成本与输入大小直接相关**：推理成本与输入大小（文本的 Token 数）和模型本身的大小有关，一般 Embedding 和 Reranker 模型大小在几百 MB 到几个 GB 不等 [cite:717][cite:719]。重排过程需要对每个候选文档进行高成本的模型推理，且每次在线查询都需重新推理，结果无法复用，带来重复开销 [cite:717][cite:719]。如果每次查询需要重排 top-10 个文档，就相当于 10 倍对单个文档离线计算 Embedding 的成本 [cite:717][cite:719]。
- **延迟与成本**：Cross-encoder Reranker 处理所有向量检索返回的文档会导致延迟显著增加，从向量检索的毫秒级提高到几百毫秒甚至几秒 [cite:717][cite:719]。假设第一阶段向量检索返回 top-100 个文档，重排这些文档的成本高达 0.001 美元，比单独执行向量搜索的成本高出 5000 倍 [cite:717][cite:719]。
- **硬件要求**：开源模型如 bge-reranker-base 在 CPU 上运行较慢，需要部署 GPU（如 A100）才能将重排速度压到 1 秒以内 [cite:718][cite:720]。

这些因素共同导致 Cross-encoder Reranker 不适合网页搜索、电商搜索等高流量、大规模候选集的信息检索系统 [cite:717][cite:719]。

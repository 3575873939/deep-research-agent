# Python 3.13 free-threading（PEP 703）生产可用性与 C 扩展兼容性调研报告

## 核心结论

- Python 3.13 的 free-threading（PEP 703）官方状态为**实验性（experimental）**，以可选变体形式发布，默认构建在所有受支持版本上仍启用 GIL [cite:374][cite:385][cite:386]。
- free-threaded 构建通过 `--disable-gil` 标志生成，与标准构建 **ABI 不兼容**，可执行文件带 `t` 后缀（如 `python3.13t`）[cite:374][cite:385]。
- 从 Python 3.14 起，free-threaded 解释器依据 PEP 779 **不再被视为实验性**，但仍不是默认解释器构建 [cite:384][cite:386]。
- 主流库已陆续声明支持：NumPy 2.1.0、pandas 2.2.3、SciPy 1.15.0、PyTorch 2.6.0 等 [cite:377]。但 PyTorch 后续宣布在 nightlies 中放弃 CPython 3.13t 支持，建议用户迁移到 CPython 3.14t [cite:379]。
- C 扩展的主要兼容性风险集中在 **GIL 依赖与线程安全标记**：未显式标记支持 free-threading 的 C-API 扩展模块会在导入时自动重新启用 GIL 并打印警告 [cite:375][cite:381]。
- 性能方面，3.13 free-threading 单线程开销约为 pyperformance 套件的 **40%**，官方目标是在 3.14 降至不超过 10% [cite:380]。

## 分述

### 1. 官方支持状态与构建方式

CPython 3.13 发布了实验性的 free-threaded 构建 [cite:374][cite:385][cite:386]。该构建是**可选变体（opt-in）**，默认构建在所有受支持版本上仍然启用 GIL，即默认构建不启用 GIL 禁用模式 [cite:374]。

- 构建标志：`--disable-gil` [cite:374][cite:385]
- ABI：与标准构建不兼容 [cite:374][cite:385]
- 可执行文件命名：带 `t` 后缀（如 `python3.13t`）[cite:374][cite:385]
- 版本演进：free-threaded 状态在 Python 3.14 起不再被视为实验性（依据 PEP 779），但仍不是默认解释器构建 [cite:386]

### 2. 主流库兼容性现状

根据 Python Free-Threading Guide 的兼容性跟踪表，以下主流库已列出支持 free-threading 的首个版本 [cite:377]：

| 库 | 首个支持版本 |
|---|---|
| NumPy | 2.1.0 |
| pandas | 2.2.3 |
| SciPy | 1.15.0 |
| PyTorch | 2.6.0 |
| scikit-learn | 1.6.0 |
| matplotlib | 3.9.0 |
| PyArrow | 18.0.0 |
| Numba | 0.65.0 |
| Cython | 3.1.0 |

Python 官方文档确认，自 3.13 起 CPython 支持 free-threading 构建，并推荐使用 py-free-threading.github.io/tracking 等网站跟踪流行包的支持状态 [cite:383]。

**重要变化**：PyTorch 后续宣布在 nightlies 中立即放弃 CPython 3.13t（free-threaded）支持，且该支持不会包含在 PyTorch 2.13 版本中。原因是上游 manylinux 项目于 2026-05-07 从 Docker 镜像中移除了 CPython 3.13t；PyTorch 建议需要 free-threaded 构建的用户迁移到 CPython 3.14t [cite:379]。

### 3. C 扩展已知兼容性问题

在 Python 3.13 free-threading 模式下，C 扩展的已知兼容性问题主要围绕 GIL 依赖与线程安全标记：

1. **未显式标记支持 free-threading 的 C-API 扩展模块会在导入时自动重新启用 GIL**，并打印警告。这是官方文档明确指出的行为，也是第三方扩展（尤其是含扩展模块的包）在 free-threaded 构建下可能无法就绪的主要原因 [cite:375][cite:381]。

2. **GIL 依赖 API 与线程安全假设**：free-threaded 构建移除了 GIL 对 Python 运行时的串行化保护，因此历史上依赖 GIL 保证线程安全的 C 扩展代码需要重新审计。PyO3 文档指出，使用 `unsafe` 并基于"Python 因 GIL 而单线程"这一历史假设编写的代码，在 free-threaded 下可能不再正确 [cite:372]。

3. **线程安全标记机制**：扩展模块可通过设置 `Py_MOD_GIL` 槽为 `Py_MOD_GIL_NOT_USED` 来声明其线程安全；若选择退出（opt-out），解释器会在导入该模块时重新启用 GIL 并打印 `RuntimeWarning`，消息中包含导致 GIL 重新启用的模块名 [cite:372]。

4. **引用计数相关**：free-threaded 构建中部分对象被"永生"（immortal），其引用计数不再被修改，以避免引用计数争用阻碍多线程扩展。截至 3.14 版本，永生化仅限于代码常量（数字字面量、字符串字面量及由其他常量组成的元组字面量）和经 `sys.intern()` 驻留的字符串 [cite:381]。这暗示引用计数语义在 free-threaded 下与常规构建存在差异，C 扩展若直接操作引用计数需注意。

5. **内置类型的线程安全**：free-threaded 构建中 `dict`、`list`、`set` 等内置类型使用内部锁来防止并发修改，行为类似 GIL；但官方建议尽可能使用 `threading.Lock` 等同步原语，而非依赖内置类型的内部锁 [cite:375][cite:381]。

6. **运行时检测**：可通过 `sys._is_gil_enabled()` 检查 GIL 是否实际被禁用，通过 `sysconfig.get_config_var("Py_GIL_DISABLED")` 判断构建是否支持 free-threading [cite:375][cite:381]。

### 4. 性能表现

Python 3.13 的 free-threading 模式是实验性功能，允许禁用 GIL 以在可用 CPU 上并行运行线程 [cite:380]。

- **单线程性能**：官方文档明确指出，该模式下单线程性能会受到很大影响。与启用 GIL 的默认构建相比，执行 Python 代码有额外开销，在 3.13 中 pyperformance 套件的开销约为 **40%**，主要原因是自由线程构建中禁用了特化自适应解释器（PEP 659）[cite:380]。
- **受影响较小的场景**：大部分时间花在 C 扩展或 I/O 上的程序受到的影响较小 [cite:380]。
- **官方目标**：到 3.14 将 pyperformance 套件开销降至不超过 10% [cite:380]。
- **技术背景**：AWS 博客指出 Python 3.13 于 2024 年 10 月正式发布并首次引入对线程自由的支持，其核心技术包括细粒度锁定、并发垃圾收集和原子引用计数，且该功能被设计为可选项而非完全移除 GIL [cite:373]。CodSpeed 的基准测试文章以 PageRank 算法为例说明，在 Python 3.12 或更早版本中，朴素的多线程实现会在矩阵运算期间受 GIL 瓶颈限制，而多进程版本则面临内存开销、进程间数据传输成本和共享状态管理复杂等问题 [cite:376]。

### 5. 后续版本路线图

- Python 3.13 首次提供了实验性的 free-threading（禁用 GIL）构建，官方 macOS 和 Windows 安装程序可选安装该构建 [cite:378]。
- 随着 PEP 779 的接受，从 Python 3.14 起 free-threaded 解释器不再被视为实验性，但尚未成为默认构建 [cite:384]。
- free-threaded 构建在运行时可通过环境变量 `PYTHON_GIL` 或命令行选项 `-X gil` 选择启用 GIL；当导入未明确标记支持 free-threading 的 C-API 扩展模块时，GIL 可能自动启用并打印警告 [cite:378]。
- 在 3.14 中，对象永生（immortalization）仅限于代码常量（数字、字符串及由其他常量组成的元组字面量）和由 `sys.intern()` 驻留的字符串 [cite:378]。
- free-threaded 构建旨在在 Python 层面提供与默认 GIL 构建相似的线程安全行为，内置类型（如 `dict`、`list`、`set`）使用内部锁防止并发修改，但建议尽可能使用 `threading.Lock` 等同步原语 [cite:378]。

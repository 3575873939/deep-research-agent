# SQLite WAL 模式与默认 rollback journal 的并发读写差异及适用场景报告

## 核心结论

1. **并发模型根本不同**：默认 rollback journal 模式通过对整个数据库文件加锁实现并发控制，写事务会阻塞读事务，读事务也会阻塞写事务，读写无法并发 [cite:617][cite:618]；WAL 模式则允许读不阻塞写、写不阻塞读，读写可并发执行 [cite:619][cite:620][cite:621]。
2. **WAL 的核心机制是"快照读 + 追加写"**：写事务将变更追加到独立的 `-wal` 文件而非直接修改数据库文件，读事务通过"结束标记"（end mark）获得某一时间点的一致快照，因此读写互不干扰 [cite:628][cite:630][cite:631]。
3. **WAL 仍是"多读单写"**：由于只有一个 WAL 文件，同一时刻只能有一个写事务，写与写之间仍然串行 [cite:627][cite:630][cite:638][cite:639]。
4. **WAL 有明确的适用边界**：适合高并发读、读多写少、小事务场景；不适用于网络文件系统、只读介质、写密集/多连接写入、超大事务等场景 [cite:634][cite:635][cite:636]。
5. **启用方式简单但需注意持久性与限制**：执行 `PRAGMA journal_mode=WAL;` 即可，设置持久生效；但需关注 checkpoint 调优、WAL 文件增长、备份兼容性等问题 [cite:624][cite:625]。

## 分述

### 一、默认 rollback journal 模式的并发行为

在默认的 rollback journal（回滚日志，默认 DELETE 模式）下，并发控制通过对整个数据库文件加锁实现，读写无法并发 [cite:617]。

**五种锁状态**：UNLOCKED（无锁）、SHARED（共享锁，可读不可写，多个读可同时持有）、RESERVED（保留锁，表示将来要写，同一时刻只能有一把，可与共享锁共存）、PENDING（未决锁，等待所有共享锁释放以获取独占锁）、EXCLUSIVE（独占锁，只有持有它才能写，与任何其他锁都不能共存）[cite:617]。

**写事务加锁流程**：加共享锁 → 加保留锁 → 将原始数据备份到回滚日志 → 在内存中修改 → 确保日志落盘 → 加未决锁 → 提交写事务 → 加独占锁 → 将修改写入数据库文件 → 确保落盘 → 删除日志文件 → 释放独占锁 [cite:617]。

**阻塞关系**：数据库文件被独占锁锁住期间读写不能并发 [cite:617]；任何写事务都会对整个数据库文件加排他锁，从而阻塞所有其他读操作和写操作 [cite:618]。因此一个长写事务会阻塞所有其他读事务，一个长读事务也会阻塞写事务 [cite:617]。隔离性方面，只有写事务提交后读连接才能看到其修改 [cite:617]。

### 二、WAL 模式的并发行为

**WAL 文件与追加写**：写事务不直接修改数据库文件，而是将变更追加到独立的 `-wal` 文件中，COMMIT 发生在提交记录被追加到 WAL 时，因此读事务可以继续从原始未修改的数据库文件中读取 [cite:630][cite:631]。

**快照读机制**：读事务开始时先记住 WAL 中最后一个有效提交记录的位置（"结束标记"），该标记在整个读事务期间保持不变，保证单个读事务只看到某一时间点的快照状态 [cite:628][cite:630]。读取某一页时，先检查 WAL 中是否存在该页在结束标记之前的副本，若有则读取 WAL 中的最新副本，否则从原始数据库文件读取 [cite:628][cite:630]。

**并发特性**：由于写事务只向 WAL 末尾追加内容，不会干扰读事务，因此读不阻塞写、写不阻塞读；但只有一个 WAL 文件，同一时刻只能有一个写事务，写写之间不能并行 [cite:627][cite:630][cite:631]。

**shm 文件与 WAL 索引**：为避免每个读事务都扫描整个 WAL 文件，SQLite 在共享内存中维护"WAL 索引"（wal-index）用于快速定位页面，对应 `-shm` 文件；这也意味着所有使用数据库的进程必须位于同一台主机上，WAL 无法在网络文件系统上工作 [cite:628][cite:630][cite:631]。

**checkpoint 机制**：checkpoint 是将 WAL 文件中的事务逐步写回原始数据库文件的过程，默认在 WAL 文件达到约 1000 页时自动执行，也可通过 `sqlite3_wal_checkpoint()` 等接口手动触发 [cite:627][cite:630][cite:631]。checkpoint 可与读事务并发运行，但当它到达超过任何当前读事务结束标记的页面时必须停止，因此长时间运行的读事务会阻止 checkpoint 取得进展 [cite:628][cite:630]。checkpoint 会记住停止位置，下次从该处继续 [cite:630]。当写操作发现整个 WAL 已全部写回并同步、且没有读事务在使用 WAL 时，写事务会将 WAL 倒回开头重新写入，以防止 WAL 文件无限增长 [cite:628][cite:630]。

**文件生成与持久性**：开启 WAL 模式后会生成 `-wal` 文件（约 6M）和 `-shm` 文件（约 100k），且 WAL 模式会持久存在，下次启动即使不执行 `PRAGMA journal_mode=WAL` 仍默认以 WAL 模式打开 [cite:627]。

### 三、两种模式的具体差异对比

1. **读写是否互相阻塞**：rollback journal 模式下写操作锁住整个数据库文件，同一时刻只能有一个写事务，其他读写都得等待 [cite:639]；WAL 模式下读取器不阻塞写入器、写入器不阻塞读取器，读写可并发 [cite:637][cite:638][cite:641]。WAL 相当于把读锁和写锁分离，写操作只获取轻量级写锁（不阻塞读），读操作只获取共享锁，与写锁互不排斥 [cite:640]。

2. **多读单写**：WAL 模式下一次只能有一个写入器，写与写之间仍串行 [cite:638][cite:639]；但多个读取器可同时存在，每个读取器拥有自己的"结束标记"，确保单个读事务看到一致状态 [cite:638][cite:641]。读取器可以存在于不同进程中 [cite:638]。

3. **跨进程并发**：WAL 模式要求所有使用数据库的进程必须位于同一台主机上，无法工作于跨网络文件系统，因为 WAL 需要所有进程共享少量内存（通过 `-shm` 共享内存文件维护 WAL 索引）[cite:637][cite:638][cite:641]。WAL 索引帮助读取器快速定位页面，提高读取器性能，但共享内存的使用意味着所有读取器必须存在于同一台机器上 [cite:638]。

4. **检查点与并发**：检查点可与读取器并发运行，但当到达超过任何当前读取器结束标记的页面时必须停止，否则可能覆盖读取器正在使用的数据库文件部分 [cite:638]。因此长时间运行的读取事务可以阻止检查点取得进展 [cite:638][cite:641]。

5. **性能差异**：WAL 在大多数场景下明显更快，磁盘 I/O 更倾向于顺序读写，使用的 `fsync()` 操作少得多 [cite:637][cite:638]。但在读非常多、写非常少的应用场景中，WAL 可能比传统 rollback-journal 方式稍慢一点点（大概 1% 或 2%）[cite:637][cite:638][cite:641]。

### 四、适用场景与不适用场景

**适用场景**：
1. 高并发读场景——WAL 提供更高并发性，读取器不阻塞写入器、写入器不阻塞读取器 [cite:634][cite:635]；
2. 读多写少场景——少量写操作不再阻塞读操作，避免响应过慢 [cite:635]；
3. 大多数情况下 WAL 明显更快，磁盘 I/O 更具顺序性，`fsync()` 操作更少 [cite:634]；
4. 适合较小事务，WAL 最适合小事务 [cite:634]。

**不适用场景**：
1. 网络文件系统——所有使用数据库的进程必须位于同一台主机，WAL 不适用于 NFS 等网络文件系统，因为要求所有进程共享少量内存 [cite:634][cite:636]；
2. 只读介质——无法打开只读 WAL 数据库，打开进程必须对 `-shm` 共享内存文件或包含数据库文件的目录具有写入权限；从 3.22.0 起，若 `-shm` 和 `-wal` 文件已存在或可创建，或数据库不可变，则可打开只读 WAL 数据库 [cite:634][cite:636]；
3. 写密集/多连接写入——WAL 模式下一次只能有一个写入器，写并发仍受限 [cite:634]；
4. 大事务——WAL 不适用于非常大的事务，大于约 100MB 的事务传统回滚日志模式可能更快，超过 1GB 的事务 WAL 可能因 I/O 或磁盘满错误而失败（注：3.11.0 起 WAL 处理大事务效率已与回滚模式相当）[cite:634][cite:636]；
5. 极少数写的场景——主要执行读取而极少写入的应用中，WAL 可能比传统回滚日志方法稍慢（约 1%-2%）[cite:634][cite:636]；
6. 多数据库事务——涉及多个附加数据库的更改事务对每个单独数据库是原子的，但整体不是原子的 [cite:634][cite:636]。

### 五、配置方式与注意事项

**启用方式**：执行 `PRAGMA journal_mode=WAL;`，该设置具有持久性，关闭并重启数据库后仍保持 WAL 模式 [cite:624][cite:625]。若底层 VFS 不支持共享内存原语，则会回退到 `journal_mode=delete`（回滚日志模式）[cite:624]。

**checkpoint 调优**：默认当 WAL 文件大小达到约 1000 页阈值时自动执行检查点，阈值可通过 `SQLITE_DEFAULT_WAL_AUTOCHECKPOINT` 编译时选项或 `PRAGMA wal_autocheckpoint` 调整 [cite:624][cite:625]。默认检查点由执行 COMMIT 的同一线程自动运行，会导致大多数 COMMIT 很快，但偶尔触发检查点的 COMMIT 会明显变慢；若不希望出现这种延迟，可关闭自动检查点，改由单独的线程或进程定期执行 [cite:625]。应用程序也可通过 `sqlite3_wal_checkpoint()` 发起 passive 类型检查点，或通过 `sqlite3_wal_checkpoint_v2()` 发起 full/restart 类型检查点 [cite:624]。

**WAL 文件增长**：WAL 文件命名为数据库文件名加 `-wal` 后缀，只要有数据库连接打开就会存在，通常在最后一个连接关闭后自动删除 [cite:624]。每当发生写入时，若整个 WAL 已传输回数据库并同步且无读取器使用 WAL，写入器会将 WAL 倒回开头，防止无限增长 [cite:625]。但长时间运行的读事务会阻止检查点推进，可能导致 WAL 文件过大，此时应考虑手动执行检查点 [cite:624][cite:625]；关闭自动检查点也可能造成 WAL 文件过大 [cite:624]。

**备份兼容性及其他限制**：
- 所有使用数据库的进程必须位于同一台主机上，WAL 不适用于网络文件系统（如 NFS）[cite:624][cite:625][cite:626]；
- 涉及多个 ATTACH 数据库的事务对每个数据库是原子的，但对所有数据库整体不是原子的 [cite:624][cite:625][cite:626]；
- 进入 WAL 模式后无法更改页面大小（page_size），必须处于回滚日志模式才能更改 [cite:625][cite:626]；
- 只读 WAL 数据库的打开需满足特定条件（`-shm` 和 `-wal` 文件已存在或可创建，或数据库为 immutable），自 3.22.0 版本起支持 [cite:624][cite:625][cite:626]；
- WAL 最适合较小事务，对于大于约 100 MB 的事务传统回滚日志模式可能更快，超过 1 GB 的事务 WAL 模式可能因 I/O 或磁盘满错误而失败 [cite:625][cite:626]。

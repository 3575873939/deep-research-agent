# MCP（Model Context Protocol）Server/Client 架构及其与 Function Calling 的关系

## 核心结论

1. **MCP 采用 client-host-server（CHS）三层架构**，而非简单的两组件 CS 架构，三个角色职责分明：Host 承载 AI 智能并唯一与 LLM 交互，Client 是无状态协议中间件，Server 是确定性能力执行器 [cite:1182][cite:1185]。

2. **MCP 支持多种传输方式**：stdio（本地进程通信）、HTTP+SSE（远程推送）以及 2025 年 3 月引入的 Streamable HTTP（单一端点、双向实时、支持会话恢复），其中 Streamable HTTP 在企业代理兼容性和断线重连方面更优 [cite:1172][cite:1174][cite:1175]。

3. **MCP 与 Function Calling 是互补关系而非竞争关系**：Function Calling 是 LLM 生成 JSON 结构调用外部工具的机制（"调用"的动作），MCP 是在此之上的标准层，为 Function Calling 提供统一规范和发现机制（"标准接口"），二者处于栈上不同的两层 [cite:1157][cite:1161]。

4. **MCP 协议在 JSON-RPC 2.0 之上定义了三大核心原语**：Tools、Resources、Prompts，对应协议方法 /list、/get 以及 tools/call [cite:1167][cite:1169]。

## 分述

### 一、MCP 的 Host / Client / Server 三层架构

MCP 采用 client-host-server（CHS）三层架构 [cite:1182][cite:1185]，三个角色职责如下：

**1. Host（宿主应用）**
- 是 AI 智能的唯一承载者，也是整个系统中唯一与 LLM 直接交互的组件 [cite:1182][cite:1185]。
- 核心任务包括：管理完整的对话上下文、动态构建和拼接 Prompt、解析 LLM 的响应、根据 AI 决策生成与 MCP Server 交互的指令 [cite:1182][cite:1185]。
- 是运行 AI 模型的应用，如 Claude Desktop、VS Code 插件、Web 应用等 [cite:1186]。
- 一个 MCP 应用的智能水平完全由其 Host 的实现质量决定 [cite:1182]。

**2. Client（客户端）**
- 是位于 Host 和 Server 之间的无状态协议中间件，在 Host 内部运行，负责与 Server 建立一对一连接 [cite:1186]。
- 严格实现 MCP 通信协议，负责协议握手、会话管理、心跳维持，并将 Host 的意图（如调用某个工具）转换为符合 MCP 规范的 JSON-RPC 请求发送给 Server [cite:1182][cite:1185]。
- 不关心业务逻辑，也不理解 AI 意图，仅作为连接 Host 与 Server 的标准化通信管道 [cite:1182]。

**3. Server（服务器）**
- 是确定性能力的执行器，是一个标准的网络服务，向外界声明并提供一组具有确定性的、可供远程调用的能力（Capabilities），如工具调用、文件操作等 [cite:1182][cite:1185]。
- 接收标准化请求，执行相应能力并返回确定结果，不包含任何 AI 逻辑，行为可预测且可靠 [cite:1182]。
- 是提供具体能力的外部程序，如数据库查询、文件操作、API 调用等 [cite:1186]。

**通信方式**：MCP 支持两种传输层协议——stdio（标准输入输出，适合本地进程通信）和 HTTP + SSE（Server-Sent Events，适合远程服务通信，支持流式响应）[cite:1186]。消息格式采用 JSON-RPC 2.0 规范，所有请求和响应遵循统一的消息结构 [cite:1186]。连接生命周期分为三个阶段：初始化（客户端与服务器交换能力信息，即 capability negotiation）、运行（正常进行请求/响应和通知消息传递）、关闭（优雅终止连接，释放资源）[cite:1186]。一个 Host 可以连接多个 Server [cite:1184]。

### 二、核心原语与消息格式

MCP 协议在业务语义层自定义了核心方法，包括 tools/call、resources/read、prompts/get 等，这些方法构建在 JSON-RPC 2.0 通用请求响应格式的消息标准层之上 [cite:1167]。

MCP 的三大原语为 Tools、Resources、Prompts，分别对应协议方法 /list、/get 以及 tools/call，通信内容采用 JSON-RPC 2.0 格式，JSON Schema 在工具定义中发挥作用 [cite:1169]。

MCP 采用客户端-服务器架构，由 MCP 服务器（负责与外部系统交互）、MCP 客户端（负责与服务器通信）和 MCP 主机（协调客户端与服务器之间的通信）三部分组成 [cite:1168]。

### 三、传输方式及适用场景

MCP 的 client 与 server 之间主要支持三种传输方式：stdio、HTTP+SSE 和 Streamable HTTP [cite:1172][cite:1175]。

| 传输方式 | 机制 | 适用场景 | 局限 |
|---|---|---|---|
| **stdio** | 基于系统标准输入输出（Unix 进程通信原理） | 本地高性能、低延迟通信，适合本地场景 | 性能受限 [cite:1173][cite:1175] |
| **HTTP+SSE** | 两个端点（GET 建立 SSE 流、POST 发送消息），SSE 提供单向实时推送 | 需要服务端推送的远程场景 | 长连接易被代理掐断、重连后会话易丢失 [cite:1174][cite:1175] |
| **Streamable HTTP** | 通信合并到单一端点（/mcp），支持 POST 和 GET，基于 HTTP/2 流式传输 | 容器化和自动扩缩容的远程部署场景 | 2025 年 3 月引入 [cite:1172][cite:1174] |

Streamable HTTP 支持双向实时交互和会话恢复，可运行无状态模式，在企业代理兼容性、连接复用、断线重连（配合 last-event-id 断点续传）方面优于 SSE [cite:1172][cite:1174]。MCP Client 支持 Stdio 与 Streamable HTTP 双模传输 [cite:1172]。

### 四、MCP 与 Function Calling 的关系与区别

**抽象层次不同**：MCP 与 Function Calling 处于不同的抽象层次，二者是互补关系而非竞争关系。Function Calling 是 LLM 模型生成 JSON 结构调用外部工具或 API 的一种机制，让模型能根据自然语言输入识别所需功能并发起调用，是 AI 实用化的基础手段；而 MCP 是在此之上的标准层，为 Function Calling 提供统一规范和发现机制，通过客户端与服务器间的 JSON-RPC 接口实现工具定义的统一广播与描述，使 AI 应用不再需要为每种模型/平台写专属集成代码 [cite:1157]。

**通俗概括**：Function Calling 是"调用"的动作，MCP 是让这种动作跨平台可靠执行的"标准接口" [cite:1157]。有观点进一步概括为：Function Call 决定"怎么叫工具"，MCP 决定"工具怎么接入"，一个是 LLM 层面的能力，一个是协议层面的标准，是栈上不同的两层 [cite:1161]。

**工程实践**：一个完整的系统会使用 MCP 来加载和管理可用工具，再通过 Function Calling 从模型端驱动具体调用，从而增强开发效率并提升系统的可维护性和互操作性 [cite:1157]。

**调用流程**：MCP 定义了工具发现、能力协商、调用格式、返回结构等协议细节，以 JSON-RPC 2.0 为基础通信方式，并支持多语言 SDK 与工具接入 [cite:1157]。MCP 的典型调用流程包括：
1. 用户向 AI Agent（作为 MCP Client）提问，Agent 将用户问题与 MCP Server/Tool 信息一起发送给 LLM；
2. LLM 推理后选出最合适的 MCP Server 和 MCP Tool 返回给 Agent；
3. Agent 直接调用该 MCP Tool 获取结果；
4. MCP Server 返回结果给 Agent；
5. Agent 再将问题与结果交给 LLM 规整；
6. 最后 LLM 返回规整内容给 Agent 并呈现给用户 [cite:1160]。

**集成方式**：MCP 基于 JSON-RPC 2.0 定义通信，工具只要实现 MCP 服务器即可被不同客户端识别，与语言、框架无关，支持多语言 SDK，这种解耦方式保证了跨平台兼容和未来扩展性 [cite:1157]。MCP 服务器可通过 STDIO（适合本地轻量场景）或 HTTP（适合远程或跨平台场景）两种模式与客户端建立连接，客户端启动时加载 MCP 配置，向服务器发起握手，双方确认会话后进入能力协商阶段 [cite:1157]。

**安全性**：MCP 强调安全治理，允许在协议层增加权限管理、工具可见性控制与审计机制；相比 Function Calling 仅依赖开发者手动校验，MCP 在架构层面提供了更统一的安全边界和可追踪的访问日志 [cite:1157]。

**在 Agent 架构中的角色**：MCP 扮演"工具注册中心"的角色，Agent 可通过 MCP 自动加载检索、数据库、API 等工具，Function Calling 则是 Agent 调用这些工具的执行方式，两者结合使 Agent 更加自治与灵活 [cite:1157]。

# FastAPI 中 SSE 与 WebSocket 在单向流式输出场景下的对比调研报告

## 核心结论

1. **协议定位差异**：SSE 是基于标准 HTTP 的服务器单向推送技术，仅支持服务器→客户端方向的数据传输 [cite:682][cite:684][cite:686]；WebSocket 是基于独立协议的全双工通讯协议，握手阶段借用 HTTP 的 101 Switching Protocols 完成协议升级 [cite:674][cite:676]。在单向流式输出场景下，SSE 的协议特性与需求天然匹配。

2. **连接开销与兼容性**：SSE 基于标准 HTTP，无需额外协议升级握手，连接开销更低，且兼容现有网络基础设施、CDN 缓存友好 [cite:679][cite:681]；WebSocket 需要一次额外的协议升级握手并建立独立 TCP 连接，对 CDN、防火墙、代理服务器的兼容性不如普通 HTTP [cite:677][cite:681]。

3. **错误恢复能力**：SSE 内置自动重连机制，支持通过 Last-Event-ID 实现消息续传 [cite:679]；WebSocket 的自动重连需要手动实现 [cite:679]。

4. **服务端资源占用**：SSE 比 WebSocket 更轻量，资源消耗更少，对服务器压力更小 [cite:677][cite:679]；WebSocket 需要独立 TCP 连接，对服务器压力更大 [cite:677]。在生产部署中处理 10 万+并发连接时，SSE 通常比 WebSocket 显示更低的 CPU 使用率（无帧掩码开销），内存消耗大致相当 [cite:668]。

5. **LLM 流式接口选择 SSE 的核心依据**：SSE 无状态、与 HTTP 基础设施兼容、故障模式可预测 [cite:667]；在 LLM 每秒 50–100 Token 的消息速率下，SSE、WebSocket 和 gRPC 流式传输的延迟基准测试结果基本一致，远未达到任何协议的吞吐量上限 [cite:667]；LLM 流式传输的核心场景是"提示输入、文本输出"，SSE 恰好擅长从服务器向客户端推送数据 [cite:669]。

6. **SSE 的局限与演进趋势**：SSE 是单向的，客户端无法通过同一连接发回消息，每个客户端操作需要单独的 HTTP 请求，导致状态协调复杂度快速上升 [cite:669]。当 AI 应用从简单聊天演进到 Agent 工作流时，SSE 的局限性变得明显，行业正在向 WebSocket 迁移 [cite:669]；MCP 协议自 2025-03-26 版本起也从 SSE 转向 Streamable HTTP [cite:671]。

## 分述

### 一、SSE 的协议特性与性能限制

SSE 是一种基于标准 HTTP 协议的服务器单向推送技术，服务器可主动将实时更新推送给客户端，无需客户端反复发起请求 [cite:682][cite:683][cite:686]。其协议特性包括：

- **连接方式**：基于 HTTP 长连接（持久连接），客户端通过 EventSource 发起 HTTP GET 请求，服务器以 `Content-Type: text/event-stream` 响应并保持连接打开 [cite:682][cite:685][cite:686]。
- **数据格式**：以 UTF-8 编码的纯文本流传输，每个消息以一对换行符（`\n\n`）结尾以区分不同事件 [cite:684][cite:685][cite:686]。
- **自动重连**：连接中断后浏览器会自动尝试重新连接，并可通过 Last-Event-ID 实现消息续传，重连间隔可由服务器端通过 retry 字段设置 [cite:682][cite:684][cite:686]。

性能限制方面：

- 不通过 HTTP/2 使用时，SSE 受浏览器对同一域名最大连接数限制（通常为 6 个），该限制针对每个浏览器+域，在打开多个选项卡时尤为明显；使用 HTTP/2 时最大连接数由服务器和客户端协商（默认约 100）[cite:685]。
- SSE 是单向通信（仅服务器→客户端），仅支持文本数据传输，不支持二进制 [cite:682][cite:684][cite:686]。
- 代理层面，使用 NGINX 代理 SSE 服务时需禁用 proxy_buffering，且该配置缺乏运行时动态启停的灵活性 [cite:686]。

### 二、WebSocket 的协议特性与性能限制

FastAPI 中 WebSocket 的实现方式：需先安装 websockets 库，然后在应用中使用 `@app.websocket("/ws")` 装饰器定义端点，端点函数接收 WebSocket 对象，先 `await websocket.accept()` 接受连接，再通过 while 循环 `await websocket.receive_text()` 接收消息、`await websocket.send_text()` 发送消息；也可使用 `from starlette.websockets import WebSocket`，FastAPI 直接提供了相同的 WebSocket 支持 [cite:672][cite:673]。

协议特性方面：

- **全双工通讯**：建立在单个 TCP 连接之上，握手阶段借用 HTTP 的 101 Switching Protocols 完成协议升级，协议标识符为 ws（加密为 wss），默认使用 80 端口、加密 TLS 连接默认使用 443 端口 [cite:674][cite:676]。
- **帧结构**：基于 Frame 而非 Stream，每个帧有严格的数据结构，包含 FIN 标志位、Opcode、Payload Length、Masking-key 和 Payload Data 等字段；Opcode 中 0x00 为数据延续帧、0x01 为 UTF-8 文本帧、0x02 为二进制帧，0x08 为关闭连接、0x09 为 Ping、0x0A 为 Pong；控制帧的 Payload 长度限制为 125 字节且不允许分片；客户端到服务器的数据需强制掩码，服务器到客户端的数据无需掩码 [cite:674]。
- **心跳机制**：通过 Ping（0x09）和 Pong（0x0A）控制帧实现 [cite:674]。

性能限制方面：控制帧 Payload 必须小于 125 字节且不允许被分片 [cite:674]；WebSocket 设计用于取代 HTTP 轮询，避免每个客户端到服务端消息都携带 HTTP 头带来的较大应用层开销 [cite:675]。

### 三、单向流式输出场景下的具体对比

| 对比维度 | SSE | WebSocket |
|---|---|---|
| 连接开销 | 基于标准 HTTP，无需额外协议升级握手，开销更低 [cite:679][cite:681] | 需一次额外协议升级握手（Upgrade: websocket），建立独立 TCP 连接，增加网络开销 [cite:677][cite:681] |
| 代理/防火墙兼容性 | 基于标准 HTTP/HTTPS，兼容现有网络基础设施，CDN 缓存友好 [cite:679][cite:681] | 使用自定义协议，对 CDN、防火墙、代理服务器兼容性不如普通 HTTP [cite:681] |
| 错误恢复 | 内置自动重连，支持 Last-Event-ID 消息续传 [cite:679] | 自动重连需手动实现 [cite:679] |
| 服务端资源占用 | 更轻量，资源消耗更少，服务器压力小 [cite:677][cite:679] | 需独立 TCP 连接，服务器压力更大 [cite:677] |

**具体案例**：ChatGPT 等大型语言模型应用使用 SSE 实现流式输出，将模型生成的每个 token 实时推送到客户端，实现打字机效果 [cite:678][cite:679]。

### 四、主流 LLM 流式接口选择 SSE 的技术决策依据

主流 LLM 提供商（OpenAI、Anthropic、Cohere、Hugging Face）普遍选择 SSE 而非 WebSocket 来流式传输 Token，其技术决策依据包括：

1. **无状态与 HTTP 基础设施兼容性**：SSE 是无状态的，能与现有 HTTP 基础设施轻松兼容，故障模式可预测。这是强有力的先验理由，但并非因为 SSE 更快 [cite:667]。

2. **性能差异不在计算层面**：在 LLM 应用产生的消息速率（每秒 50–100 个 Token）下，SSE、WebSockets 和 gRPC 流式传输的延迟基准测试结果基本一致，远未达到任何协议的吞吐量上限。真正重要的是故障模式特征 [cite:667]。在生产部署中处理 10 万+并发连接时，SSE 通常比 WebSocket 显示更低的 CPU 使用率（无帧掩码开销）；内存消耗大致相当，因为两者都为每个客户端维护一个 TCP 连接。真正的性能差异是运维层面的，而非计算层面的 [cite:668]。

3. **单向流式足够满足核心场景**：LLM 流式传输的核心场景是"提示输入、文本输出"，SSE 恰好擅长从服务器向客户端推送数据 [cite:669]。对于聊天场景，用户已有 REST API 发送提示，SSE 只是返回通道 [cite:668]。规则是：聊天响应、摘要、代码生成等只读场景使用 SSE [cite:670]。

4. **简单性与标准化**：SSE 的 EventSource API 是 WHATWG HTML Living Standard 的一部分，浏览器和大多数 HTTP 客户端都支持流式响应 [cite:670]。SSE 简单、基于 HTTP 且支持自动重连 [cite:671]。

5. **故障模式更可控**：SSE 的故障模式可预测。虽然 SSE 在代理层可能因缓冲而失效（需设置 proxy_buffering off 和心跳消息），但这些问题有明确解决方案 [cite:667]。相比之下，WebSocket 在背压层失效——协议没有内置机制让服务器检测客户端消费速度，慢速客户端可能导致服务器内存无限累积 [cite:667]。SSE 连接是无状态的，重新建立成本更低，惊群效应不如 WebSocket 严重 [cite:667]。

6. **WebSocket 的复杂性代价**：WebSocket 需要处理背压监控（socket.bufferedAmount）、每客户端写入超时、缓冲区大小限制等，否则在高负载下必然出问题 [cite:667]。WebSocket 重连需要 TCP 握手、TLS 协商和 HTTP 升级往返，在大规模场景下可能产生惊群效应 [cite:667]。

7. **SSE 的局限性与演进**：SSE 是单向的，客户端无法通过同一连接发回消息，每个客户端操作需要单独的 HTTP 请求（取消生成、引导 Agent、确认工具调用等），导致状态协调复杂度快速上升 [cite:669]。当 AI 应用从简单聊天演进到 Agent 工作流（需要工具调用、用户中断、多轮对话）时，SSE 的局限性变得明显，行业正在向 WebSocket 迁移 [cite:669]。MCP 协议自 2025-03-26 版本起也从 SSE 转向 Streamable HTTP，以解决串流恢复、长连接负载和单向通讯的限制 [cite:671]。

### 五、FastAPI 实现 LLM 流式输出的代码模式与部署注意事项

**SSE 关键代码模式**：SSE 是 LLM 流式输出的首选方案，简单、浏览器原生支持、与 OpenAI 格式兼容 [cite:687]。实现上使用 FastAPI 的 StreamingResponse，该响应类型会保持与客户端的连接并持续分块返回响应 [cite:689]。核心逻辑是：调用 LLM 时设置 `stream=True`，模型以一次一个 chunk 的方式返回内容，然后通过 yield 将每个 chunk 的内容实时发送回客户端 [cite:689]。SSE 基于普通 HTTP，每条消息以 `data:` 开头后跟 JSON 负载，消息之间用两个换行符分隔，流以 `data: [DONE]` 结束 [cite:690]。

**WebSocket 关键代码模式**：WebSocket 在 FastAPI 中有原生支持，API 设计良好 [cite:687]。适用于需要双向通讯的场景，如实时对话、多人协作、低延迟需求 [cite:687]。

**选型对比**：SSE 为单向（Server→Client）通讯，基于 HTTP 协议，通过普通 HTTP 请求建立连接，浏览器原生支持自动重连，不支持二进制数据，防火墙兼容性好；WebSocket 为全双工通讯，基于独立 WebSocket 协议，通过升级握手建立连接，需手动实现重连，支持二进制数据，防火墙兼容性一般 [cite:687]。经验法则：只需服务器推送用 SSE，需要双向通讯、传输二进制或极低延迟用 WebSocket [cite:687]。

**部署注意事项（Nginx）**：SSE 端点配置需禁用代理缓冲以确保实时推送（`proxy_buffering off`），禁用缓存（`proxy_cache off`），设置长连接超时（`proxy_read_timeout 3600s`、`proxy_send_timeout 3600s`），使用 HTTP/1.1 并保持连接（`proxy_http_version 1.1`）[cite:687]。生产环境还需考虑连接池、心跳保活、背压控制、限流熔断等因素 [cite:687]。

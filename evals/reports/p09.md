# FastAPI 生产部署 ASGI 服务器选型报告：uvicorn、hypercorn 与 gunicorn

## 核心结论

1. **通用生产标准做法是 Gunicorn 作为进程管理器 + Uvicorn 工作进程**：通过 `-k uvicorn.workers.UvicornWorker` 组合，由 Gunicorn 负责进程管理（启动、健康监控、崩溃重启、请求分发、优雅信号处理），Uvicorn 负责高性能 ASGI 请求处理 [cite:1237][cite:1238][cite:1240][cite:1247][cite:1252]。

2. **Uvicorn 单独使用缺少进程管理能力**：单进程崩溃会导致应用下线，且每实例仅利用单核 CPU，无法管理多工作进程以利用多核 [cite:1238][cite:1239]。但其内存占用较低，基于 uvloop 和 httptools 可管理数千并发连接 [cite:1239][cite:1240]。

3. **Hypercorn 的核心优势是协议覆盖最全面**：支持 HTTP/1.1、HTTP/2、HTTP/3 及 WebSocket，配置灵活，适合需要前沿协议或复杂部署策略的生产环境 [cite:1257]。

4. **Kubernetes 环境建议与通用做法不同**：官方建议不使用 Gunicorn，而是在每个容器中运行单个 Uvicorn 进程，由 Kubernetes 负责进程复制与编排 [cite:1248][cite:1251]。

5. **协议能力是根本分水岭**：ASGI 协议（Uvicorn、Hypercorn 所基于）天然支持 WebSocket 和 HTTP/2，而 WSGI（Gunicorn 原生）不支持 WebSocket 或 HTTP/2 [cite:1240]。

## 分述

### 一、Uvicorn：高性能单进程 ASGI 服务器

**协议与性能**：Uvicorn 原生支持 HTTP/1.1、HTTP/2 和 WebSocket [cite:1240]，具备 WebSocket 实时双向通信和 HTTP/2 支持 [cite:1239]。基于 uvloop 和 httptools，处理能力约 45,000 req/s [cite:1253]。

**并发模型与资源占用**：并发模型为单进程异步并发，单线程处理高并发 I/O，可管理数千并发连接，每实例仅利用单核 CPU，内存占用较低（单进程、共享内存）[cite:1239][cite:1240]。

**局限**：本身缺少进程管理功能，单进程崩溃会导致应用下线，也无法管理多工作进程以利用多核 [cite:1238]。

**适用场景**：实时通信（WebSocket）场景适合 Uvicorn + Starlette [cite:1253]；在 Kubernetes 等容器编排环境中，推荐每个容器运行单个 Uvicorn 进程 [cite:1248][cite:1251]。

### 二、Hypercorn：协议覆盖最全面的 ASGI 服务器

**协议支持**：核心优势在于协议覆盖最全面，支持 HTTP/1.1、HTTP/2、HTTP/3 及 WebSocket [cite:1257]。

**配置灵活性**：可自定义事件循环（如 uvloop）和负载均衡策略 [cite:1257]。

**实测性能**：成功率为 99.97%，延迟表现稳定（平均 117.2ms）[cite:1257]。

**适用场景**：需要前沿协议（如 HTTP/3）或复杂部署策略的生产环境；若追求协议全面性，Hypercorn 因支持 HTTP/3 而被推荐用于面向未来的技术栈 [cite:1257]。

**并发模型**：现有材料未提供具体说明 [unverified]。

### 三、Gunicorn：进程管理器角色

**与 Uvicorn 的配合模式**：Gunicorn 在生产环境中通常作为进程管理器与 Uvicorn 工作进程配合使用——Gunicorn 负责启动多个工作进程、监控健康状况并在崩溃时重启、在可用工作进程间分发传入请求、优雅处理服务器信号（如零停机重启）；Uvicorn 工作进程则借助其高性能 ASGI 能力处理请求 [cite:1252]。

**ASGI 支持方式**：Gunicorn 本身主要是 WSGI 服务器，但通过专用的 Uvicorn 工作类（`uvicorn.workers.UvicornWorker`）可充当 ASGI 应用的进程管理器 [cite:1252]。此外，Gunicorn 也提供原生 ASGI worker，可在不依赖 Uvicorn 等外部组件的情况下运行 FastAPI、Starlette、Quart 等异步框架 [cite:1255]。

**并发模型**：采用预分叉（pre-fork）多进程模型，提前分配 Worker 进程，并自动重启崩溃的 Worker 以提升服务可靠性 [cite:1253]；由 master 进程管理 worker 池 [cite:1237][cite:1238]。原生为同步阻塞模型，依赖多进程/线程处理并发 [cite:1240]。

**典型部署命令**：`gunicorn -w 4 -k uvicorn.workers.UvicornWorker main:app` [cite:1252][cite:1253]。

**原生 ASGI worker 推荐生产配置**：workers=4、worker_connections=1000、keepalive=5、timeout=120、graceful_timeout=30，并可自动使用 uvloop [cite:1255]。

**工作进程数量**：常见起始点为 (2 × CPU 核心数) + 1，但最佳数量取决于应用工作负载（CPU 密集型还是 I/O 密集型）以及模型推理的性质，需要试验并监控性能来确定；对于 CPU 密集型推理任务，工作进程数多于 CPU 核心数可能因上下文切换而导致收益递减 [cite:1238][cite:1247][cite:1252]。

**适用场景**：生产 API 服务推荐 Gunicorn + Uvicorn + Starlette 组合，以多进程管理加异步 Worker 提升并发能力 [cite:1253]。

### 五、按部署环境与负载特征选型

**通用生产环境**：使用 Gunicorn 作为进程管理器，配合 Uvicorn 工作进程（`-k uvicorn.workers.UvicornWorker`）[cite:1247]。直接使用 `uvicorn main:app` 缺少进程管理，单进程崩溃会导致应用下线，也无法利用多核处理并发请求 [cite:1247]。

**工作进程数量调整**：常见起点为 (2 × CPU 核心数) + 1，但最佳值取决于应用是 CPU 密集型还是 I/O 密集型以及模型推理性质，需通过试验和监控确定；对于 CPU 密集型推理任务，工作进程数超过 CPU 核心数可能因上下文切换导致收益递减 [cite:1247]。

**Docker 容器化环境**：可将 Gunicorn+Uvicorn 命令写入 Dockerfile 的 CMD，并通过环境变量（如 WORKERS、PORT、APP_MODULE）灵活配置不同部署环境的工作进程数和端口，绑定 0.0.0.0 以便容器外部访问 [cite:1247]。

**Kubernetes 等容器编排环境**：官方建议不使用 Gunicorn，而是在每个容器中运行单个 Uvicorn 进程 [cite:1248][cite:1251]。可从零构建 Docker 镜像，CMD 直接使用 `uvicorn app.main:app --host 0.0.0.0 --port 80`，由 Kubernetes 负责进程复制与编排 [cite:1251]。

**协议前沿需求**：若追求协议全面性（如 HTTP/3），推荐 Hypercorn [cite:1257]。
